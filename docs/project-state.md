# wiiuport — project state

Factual capability inventory. Epic intent is in `docs/project-goals.md`.
Every item is `verified`, `partial`, `blocked`, or `missing`.

**Current focus.** Transform substitution. ST-PRESENT and ST-NULLDIFF are answered: the runtime
presents its own frame, and a replay of a recorded frame is byte-identical to the frame the title
presented. What remains between here and an interpolated frame is substituting the view transform
at `OnUniformAssembly` and retaining two frames rather than one, because blending needs N and N+1
and only the last complete frame is kept.

## Comparison baseline

**Baseline: upstream Cemu (`cemu-project/Cemu`), used as a standalone application.**
A user today runs the Cemu AppImage, points it at a WUX, and plays at the title's own
simulation rate with community graphic packs for resolution and shading. Upstream offers
no mechanism to re-issue a frame with substituted transform state, so a 30 Hz title
presents at 30 Hz. Every item below states its difference from that baseline.

| ST-RECORD | A frame's guest draw stream can be recorded for replay | partial | `FrameRecording` holds a frame's display lists and assembled uniform buffers by copy; `RecordingObserver` fills it from the fork's hooks. Measured on the real title through the runtime's own control channel (`GET /counters`, 12 of 12 polls answered): frames advancing to 1,642 with 487,340 display lists and 4,471,932 uniform assemblies, 0 refused incomplete, a steady ~262 lists and ~1,290 assemblies in ~306 KB per frame. | ST-REPLAY | A recorded frame replays with substituted transform state | partial | `LatteFrameHooks::SubmitDisplayList` feeds a recorded buffer back through `LatteCP_processCommandBuffer` on its own `DrawPassContext`, so a replay cannot leave half a draw pass in the stream the guest is mid-way through. `FrameReplayer` is armed one frame at a time over `POST /replay`. Measured on the real title: 1 replay, 288 lists submitted, 0 refused, and the runtime kept answering for 6 further polls with frames advancing 1,133 to 2,035. Faithfulness is now measured rather than assumed: the replayed frame is byte-identical to the one the title presented (ST-NULLDIFF). Exact gap: no transform is substituted yet, so a replay reproduces the recorded frame instead of an interpolated one. |
| ST-REPLAY-GL | Interpolation under the OpenGL renderer | missing | Deliberately out of scope: the assembly site used for substitution is the Vulkan renderer's. OpenGL presents at the guest rate. |
| ST-CAMERA | The view transform is located at run time by what its values do | verified | `interp::TransformSearch` finds it by behaviour, never from a table of offsets. Measured in gameplay: 9,982 spans across 211 shaders over 4,658 frames, rejecting 991 as varying within a frame, 5,379 as never changing and 3,472 as not a rotation, leaving 140 candidates of which the top is carried by 65 unrelated shaders at differing offsets with rotation error 1.19e-07 and a mean step of 2,967.6. The same run on a title screen finds nothing and says so with its denominators, which is the negative case the search was built to report. Six tests cover each rejection class. |
| ST-NULLDIFF | Null-interpolation discriminator: replay at t=1 is byte-identical to the original frame | verified | `tools/null_diff.py` runs three arms against a moving view at 1920x1080. The control -- present the same buffer again, replaying nothing -- is byte-identical over all 6,220,800 bytes, which is what makes the third arm readable at all. The replay arm then redraws the recorded frame, presents it through the runtime's own present, and captures it: 36 lists replayed, 1 runtime present, 0 bytes differ (largest 0). The tool refuses a run whose view never moved, so a title screen cannot pass it by having nothing to get wrong. The instrument has shown the other answer on the same code path: before ST-PRESENT's defect was fixed the same control reported 11,704 differing bytes in a 45x135 box, which was a real difference in the wrong screen's buffer. |
| ST-PRESENT | The runtime presents a frame of its own between the guest's swaps | verified | `LatteFrameHooks::SubmitPresent` assembles the guest's own two packets -- `IT_HLE_COPY_COLORBUFFER_TO_SCANBUFFER` (0xF3) and `IT_HLE_TRIGGER_SCANBUFFER_SWAP` (0xF8) -- in big-endian and feeds them through the same command processor, so the encoding stays with the code that owns it and the runtime supplies only arguments it observed. A nested present is refused, and `InRuntimePresent()` keeps the runtime's own swap from publishing a frame end the guest never reached. Which screen is presented is the whole of the difficulty: a title copies to a scan buffer twice per frame, once for the TV and once for the GamePad -- measured at 922 presents across 460 frames of Wind Waker HD -- so keeping the last one presented the GamePad's buffer into the window the user watches, and a control that should have been byte-identical came back with a GamePad item icon drawn across it. The target bits are now decoded at the hook boundary, where Latte owns them, and `FramePresenter` keeps the TV's arguments; a GamePad-only observation is refused by name rather than presented to the wrong screen. `GET /counters` reports presents observed split by screen. |
| ST-SHADOW | Substituted transform storage never writes back to guest memory | missing | Depends on ST-REPLAY. |
| ST-COUNTERS | Runtime reports frames recorded/replayed, bailouts by reason, substituted slots, all with denominators | missing | Required before any interpolation claim. |
| ST-CONTROL | Opt-in control channel for input injection, frame stepping, counters, capture | partial | `lucent::http::Server`, loopback only, opened only when `WIIUPORT_CONTROL_PORT` is set. Live routes: `GET /counters`, `GET /transforms`, `GET /capture`, `GET /controllers`, `GET /setup`, `POST /replay`, `POST /capture`, `POST /present`, `POST /nulldiff`, `POST /input`. Input injection is measured on the real title: 4,638 of 4,660 gamepad reads driven, which is what first carried a run into gameplay. Framebuffer capture is live over `POST /capture` and `GET /capture`: `FrameCapture` arms the upstream one-shot screenshot request, which hands back the presented scan buffer before the imgui overlay, and returns `std::nullopt` so no on-screen notification fires. The body is self-describing (`WIIUIMG1` magic, 16-byte header) and `tools/wiiuport/image.py` refuses a short, foreign, truncated or zero-size body by naming which. Measured on the real title: four 1920x1080 captures delivered in one run. Exact gap: no frame stepping, and capture observes only the guest's present, so it cannot show a replay's own output (ST-PRESENT). |
| ST-SHELL | First-party host shell: the runtime's own window, no Cemu UI | partial | `src/wiiuport/shell/` builds `external/cemu/bin/wiiuport`, an executable with no wxWidgets in it at all: `CemuBin` and the wx front end are excluded from the build, and `WindowSystemBridge.cpp` implements the core's ~25-function `WindowSystem` seam over an SDL3 window the shell owns. Measured on the real title offscreen: the shell boots Wind Waker HD and the runtime sees its frames (4 frames, 150 display lists, 120 uniform assemblies, 11 presents observed) with the control channel answering. Getting there fixed four layering defects in the fork at their owners rather than copying them into the shell: the Vulkan loader was initialised only by the wx app, `g_isGPUInitFinished` was defined in the entry point, the mlc layout lived in `CemuApp` (now `Cafe/Filesystem/MlcStorage`), and the whole system bring-up sequence lived in `main.cpp` (now `Boot/SystemBringup`, called by both front ends). It now has a UI of its own: RmlUi through `shared/setup-ui`, pinned beside the RmlUi checkout it renders through (ST-SETUP). Exact gaps: no window chrome or in-app settings beyond first-run setup, and the project still has no `run.sh` launcher. SDL3 is built with the X11 and Vulkan backends but not Wayland, so a Wayland session runs the shell through XWayland: wxWidgets and SDL3 both embed the generated `wp_pointer_warp_v1` protocol stubs in their static libraries, and linking the two together is a duplicate-symbol error. Enabling the Wayland backend is part of retiring the wx front end, not a separate fix. |
| ST-SETUP | A player with no command line is asked for their game, once | verified | `shell/SetupScreen` shows `shared/setup-ui`'s RmlUi screen in its own SDL3 window when nothing is configured, and `shell/TitleSelection` remembers the answer at `<config>/Cemu/selected-title.txt` so the next launch needs no argument. The disc image is adopted where the player keeps it, never copied. The picker is SDL3's own `SDL_ShowOpenFileDialog`. Proven on both branches by `tools/setup_screen.py`, which is why the screen cannot be a window that merely exists: with nothing remembered the product reports `the setup screen is on the display, waiting at 'collecting', handed 0 selections` and the display itself holds 2,073,600 pixels in 923 colours (a blank window is refused below 16), and with a title remembered the same installation reaches a frame without ever registering a screen. `GET /setup` is what makes that askable while the screen blocks the product; a build with no host to show one answers `hostReports:false` rather than a closed screen. Title identity has one owner, shared by the screen's validator and the launch path, so a file the screen accepts cannot be refused a moment later. 12 C++ tests cover the remembered answer, including a title that stopped working and an empty record. |
| ST-PAD | A gamepad is mapped automatically and can be swapped mid-game | verified | `shell/ControllerAutoMap` attaches the first SDL gamepad to player 1's emulated GamePad and applies 25 bindings laid out by position, so the button under the thumb is the one the Wii U had there; the table is checked against the working profile it was derived from. Hotplug works because the host now owns SDL's event queue and hands controller events to the provider, which upstream ran on a thread of its own -- two loops over one queue would have stolen each other's events. Measured on the real title with `tools/controller_hotswap.py`, which creates a genuine kernel input device while the game runs: before, `attached nothing, 0 attached and 0 lost`; after plugging in, `Xbox 360 Controller with 25 bindings, 1 attached`; after pulling it out, `1 attached and 1 lost`. The tool refuses if the kernel never published the device, so a silent host cannot be blamed for one that was never created. `GET /controllers` reports the same, and says `hostReports:false` in a build with no host attaching pads rather than reporting an empty state that reads as "no pad". |

| ST-HEADLESS-GAME | A maintainer run reaches gameplay in that environment | verified | A driven offscreen run reaches gameplay: 12 presses queued, 4,638 of 4,660 gamepad reads driven, 211 shaders (against 60 on the title screen) and a view transform shared by 65 unrelated shaders moving 2,967 units a frame. | ST-VERIFIER | Canonical Python verifier carrying format, tidy, structure, and test gates | partial | `tools/verify.py` runs ruff, pytest, a non-mutating `clang-format` check, the three syntax-aware ownership rules on the real libclang AST, and source-size limits; 5 of 5 gates pass over 40 tests. The ownership gate is proven on both classes: an accepted fixture reports nothing and a rejected one reports seven findings across all three rules (ISSUE-002). `.clang-tidy` is configured and confirmed (`--dump-config` keeps `clang-diagnostic-*`, `--list-checks` reports 251 active).
