# wiiuport — project state

Factual capability inventory. Epic intent is in `docs/project-goals.md`.
Every item is `verified`, `partial`, `blocked`, or `missing`.

**Current focus.** Making a recorded frame the frame the view was found in (ISSUE-006). The
substitution path is built and measured end to end: `POST /interpolate?t=` blends the view between
the last two frames the search saw and writes it into the runtime's own replayed draws, and
`tools/interpolated_frame.py` requires the resulting image to differ. It does not yet, and the
instrument says why at each stage rather than as one number. Building it found the defect that had
made every earlier replay meaningless: the frame's real command buffers enter Latte through the TCL
queue path, which was never hooked, so recordings held state with no geometry and replays issued
zero draws. With that fixed a replay draws, but the frame it replays holds a different pass from
the one the view transform lives in.

## Comparison baseline

**Baseline: upstream Cemu (`cemu-project/Cemu`), used as a standalone application.**
A user today runs the Cemu AppImage, points it at a WUX, and plays at the title's own
simulation rate with community graphic packs for resolution and shading. Upstream offers
no mechanism to re-issue a frame with substituted transform state, so a 30 Hz title
presents at 30 Hz. Every item below states its difference from that baseline.

| ST-RECORD | A frame's guest draw stream can be recorded for replay | partial | `FrameRecording` holds a frame's display lists and assembled uniform buffers by copy; `RecordingObserver` fills it from the fork's hooks. Measured on the real title through the runtime's own control channel (`GET /counters`, 12 of 12 polls answered): frames advancing to 1,642 with 487,340 display lists and 4,471,932 uniform assemblies, 0 refused incomplete, a steady ~262 lists and ~1,290 assemblies in ~306 KB per frame. | ST-REPLAY | A recorded frame replays with substituted transform state | partial | `LatteFrameHooks::SubmitDisplayList` feeds a recorded buffer back through `LatteCP_processCommandBuffer` on its own `DrawPassContext`, so a replay cannot leave half a draw pass in the stream the guest is mid-way through. `FrameReplayer` is armed one frame at a time over `POST /replay`. Measured on the real title: 1 replay, 288 lists submitted, 0 refused, and the runtime kept answering for 6 further polls with frames advancing 1,133 to 2,035. A replay now demonstrably draws: with the TCL-queue command buffers hooked (`LatteCP_itIndirectBufferDepr`, previously unobserved, which is why every earlier replay was state without geometry) one measured replay of 16 recorded buffers walked 1,408 packets, issued 36 draws and produced 64 uniform assemblies of the runtime's own, matching the 64 the recording held. Substitution is wired: `interp::TransformSubstitution` writes a blended view into those assemblies and `interp::FrameInterpolator` arms the blend, the replay and the captured pair together, refusing by name when there is no view, when `t` is outside the two frames, or when a replay is in flight. Exact gap: the frame a replay re-issues does not contain the view-carrying shaders, so arming is now refused by name (`no view transform found yet`) rather than producing an identical frame; the slots offered are restricted to shaders that drew in the most recent frame, and every guest draw is counted by origin -- 152,215 from command buffers, 0 from the ring -- and `GET /frames` reports the shape of the last 32 published frames, which shows they do not alternate -- every one holds the same 10 to 12 shaders, so the recorder is consistently missing the world pass rather than splitting frames in half (ISSUE-006). |
| ST-REPLAY-GL | Interpolation under the OpenGL renderer | missing | Deliberately out of scope: the assembly site used for substitution is the Vulkan renderer's. OpenGL presents at the guest rate. |
| ST-CAMERA | The view transform is located at run time by what its values do | verified | `interp::TransformSearch` finds it by behaviour, never from a table of offsets. Measured in gameplay: 9,982 spans across 211 shaders over 4,658 frames, rejecting 991 as varying within a frame, 5,379 as never changing and 3,472 as not a rotation, leaving 140 candidates of which the top is carried by 65 unrelated shaders at differing offsets with rotation error 1.19e-07 and a mean step of 2,967.6. The same run on a title screen finds nothing and says so with its denominators, which is the negative case the search was built to report. Six tests cover each rejection class. |
| ST-NULLDIFF | Null-interpolation discriminator: replay at t=1 is byte-identical to the original frame | partial | The instrument is now readable and the measurement is not yet conclusive. `tools/null_diff.py`'s control -- present the same buffer again, replaying nothing -- is byte-identical over all 6,220,800 bytes, which it was not before ST-PRESENT's screen defect was fixed (11,704 bytes differed in a 45x135 box that turned out to be a GamePad item icon). The replay arm then reports 0 bytes differing over 36 replayed lists and one runtime present. Exact gap: that result cannot yet distinguish a faithful replay from one that drew nothing, because the replay redraws the frame that is already in the colour buffer -- both produce the same image. The counters say so plainly: a run that replayed 470 lists reported 0 display lists and 0 uniform assemblies coming back from the runtime's own submissions, which is either a replay whose draws reused unchanged uniforms or a replay that never drew. The discriminator now exists and runs: `tools/interpolated_frame.py` substitutes a blended view into the replay and requires the image to change. Its first run answered the open question -- the replay was issuing **zero** draws over 532 packets, so "identical" meant "drew nothing" -- and the cause was an unhooked command-buffer path, now fixed. Exact gap: the replayed frame does not contain the view-carrying shaders, so the substitution writes nothing and the image is still identical for a different reason (ISSUE-006). |
| ST-PRESENT | The runtime presents a frame of its own between the guest's swaps | verified | `LatteFrameHooks::SubmitPresent` assembles the guest's own two packets -- `IT_HLE_COPY_COLORBUFFER_TO_SCANBUFFER` (0xF3) and `IT_HLE_TRIGGER_SCANBUFFER_SWAP` (0xF8) -- in big-endian and feeds them through the same command processor, so the encoding stays with the code that owns it and the runtime supplies only arguments it observed. A nested present is refused, and `InRuntimePresent()` keeps the runtime's own swap from publishing a frame end the guest never reached. Which screen is presented is the whole of the difficulty: a title copies to a scan buffer twice per frame, once for the TV and once for the GamePad -- measured at 922 presents across 460 frames of Wind Waker HD -- so keeping the last one presented the GamePad's buffer into the window the user watches, and a control that should have been byte-identical came back with a GamePad item icon drawn across it. The target bits are now decoded at the hook boundary, where Latte owns them, and `FramePresenter` keeps the TV's arguments; a GamePad-only observation is refused by name rather than presented to the wrong screen. `GET /counters` reports presents observed split by screen. |
| ST-SHADOW | Substituted transform storage never writes back to guest memory | missing | Depends on ST-REPLAY. |
| ST-COUNTERS | Runtime reports frames recorded/replayed, bailouts by reason, substituted slots, all with denominators | partial | `GET /counters` reports how far each runtime submission got -- submissions, packets the command processor walked, draws issued -- and what the substitution did with the assemblies that came back, split by reason: substituted, unarmed, not carrying the view, buffer too short. `GET /substitution` reports the two shader key sets side by side, which is what turned "none of them carried it" from a number into a readable finding (ISSUE-006). Exact gap: no per-frame timing or pacing counters, which ST-60 needs. |
| ST-CONTROL | Opt-in control channel for input injection, frame stepping, counters, capture | partial | `lucent::http::Server`, loopback only, opened only when `WIIUPORT_CONTROL_PORT` is set. Live routes: `GET /counters`, `GET /transforms`, `GET /capture`, `GET /controllers`, `GET /setup`, `POST /replay`, `POST /capture`, `POST /present`, `POST /nulldiff`, `POST /input`. Input injection is measured on the real title: 4,638 of 4,660 gamepad reads driven, which is what first carried a run into gameplay. Measured on the real title: four 1920x1080 captures delivered in one run. Exact gap: no frame stepping, and capture observes only the guest's present, so it cannot show a replay's own output (ST-PRESENT). |
| ST-SHELL | First-party host shell: the runtime's own window, no Cemu UI | partial | `src/wiiuport/shell/` builds `external/cemu/bin/wiiuport`, an executable with no wxWidgets in it at all: `CemuBin` and the wx front end are excluded from the build, and `WindowSystemBridge.cpp` implements the core's ~25-function `WindowSystem` seam over an SDL3 window the shell owns. Measured on the real title offscreen: the shell boots Wind Waker HD and the runtime sees its frames (4 frames, 150 display lists, 120 uniform assemblies, 11 presents observed) with the control channel answering. Getting there fixed four layering defects in the fork at their owners rather than copying them into the shell: the Vulkan loader was initialised only by the wx app, `g_isGPUInitFinished` was defined in the entry point, the mlc layout lived in `CemuApp` (now `Cafe/Filesystem/MlcStorage`), and the whole system bring-up sequence lived in `main.cpp` (now `Boot/SystemBringup`, called by both front ends). It now has a UI of its own: RmlUi through `shared/setup-ui`, pinned beside the RmlUi checkout it renders through (ST-SETUP). Exact gaps: no window chrome or in-app settings beyond first-run setup, and the project still has no `run.sh` launcher. SDL3 is built with the X11 and Vulkan backends but not Wayland, so a Wayland session runs the shell through XWayland: wxWidgets and SDL3 both embed the generated `wp_pointer_warp_v1` protocol stubs in their static libraries, and linking the two together is a duplicate-symbol error. Enabling the Wayland backend is part of retiring the wx front end, not a separate fix. |
| ST-SETUP | A player with no command line is asked for their game, once | verified | `shell/SetupScreen` shows `shared/setup-ui`'s RmlUi screen in its own SDL3 window when nothing is configured, and `shell/TitleSelection` remembers the answer at `<config>/Cemu/selected-title.txt` so the next launch needs no argument. The disc image is adopted where the player keeps it, never copied. The picker is SDL3's own `SDL_ShowOpenFileDialog`. Proven on both branches by `tools/setup_screen.py`, which is why the screen cannot be a window that merely exists: with nothing remembered the product reports `the setup screen is on the display, waiting at 'collecting', handed 0 selections` and the display itself holds 2,073,600 pixels in 923 colours (a blank window is refused below 16), and with a title remembered the same installation reaches a frame without ever registering a screen. `GET /setup` is what makes that askable while the screen blocks the product; a build with no host to show one answers `hostReports:false` rather than a closed screen. | ST-PAD | A gamepad is mapped automatically and can be swapped mid-game | verified | `shell/ControllerAutoMap` attaches the first SDL gamepad to player 1's emulated GamePad and applies 25 bindings laid out by position, so the button under the thumb is the one the Wii U had there; the table is checked against the working profile it was derived from. Hotplug works because the host now owns SDL's event queue and hands controller events to the provider, which upstream ran on a thread of its own -- two loops over one queue would have stolen each other's events. Measured on the real title with `tools/controller_hotswap.py`, which creates a genuine kernel input device while the game runs: before, `attached nothing, 0 attached and 0 lost`; after plugging in, `Xbox 360 Controller with 25 bindings, 1 attached`; after pulling it out, `1 attached and 1 lost`. The tool refuses if the kernel never published the device, so a silent host cannot be blamed for one that was never created. `GET /controllers` reports the same, and says `hostReports:false` in a build with no host attaching pads rather than reporting an empty state that reads as "no pad". |
